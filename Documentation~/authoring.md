# KitchenLib Studio bundle projects

Open **KitchenLib Studio → GDO Bundle Graph**, choose **Create Bundle Project**, select an existing parent folder under `Assets`, and enter a project name. Studio creates `<parent>/<project>/<project>.asset` with owned `GDOs` and `Content` folders. The graph is the bundle descriptor: only its local GDO members are built. Use **Open Bundle Project** to reopen it.

Create GDOs from the graph, choose a generated type from the inheritance-based **Create GDO** submenus, and enter the GDO name. Related types are grouped beneath their highest creatable ancestor; for example, Appliance types appear under **Create GDO → Appliance**. Studio derives the path in `GDOs` and the negative runtime ID from the normalized `project:gdo` identity. Relationships and external references are authored in the graph; expanded GDO nodes expose intrinsic fields and prefab references. Save the project before closing Unity. Build writes `Build/<project>/content/<project-slug>.assets` and a package audit report.

New GDO companions (intrinsic values, localization and relationship projections) are stored in `<project>/Editor/Overlays/<GDO-guid>.asset`. Transfer the complete project folder and its `.meta` files to preserve authored data and GUID references. Referenced prefabs and other content must also be transferred; keep those in `Content`. Existing shared companions under `Assets/ModContent/Editor/KitchenLibStudioOverlays` remain readable, including older YAML. For an existing project, choose **Collect Project Overlays** to move its shared companions into the owned folder while preserving their GUIDs, then transfer the project.

Every local member must remain under the project's `GDOs` folder. Moving it elsewhere produces a member-specific blocking diagnostic and stops a build before any output is created. Creating a GDO preflights calculated-ID collisions with local and known external references.

Use **Delete GDO…** on a resolved local node to delete it from the graph and permanently remove its project-owned GDO asset and companion. Studio always asks for confirmation and names the GDO; confirming also removes its relationships and connected edges, and the filesystem deletion cannot be undone. Canceling leaves the graph and files unchanged, and a deletion failure restores the original graph and owned assets. External references use **Remove Reference** instead: this removes only the graph record, its relationships and connected edges because Studio does not own external source data. Broken records remain graph-only removals. Relationship nodes retain their own removal action.

## Supported editor extension API

Intentional C# extension contracts live under `KitchenLib.Studio.Editor.Api` in the editor-only `KitchenLib.Studio.Editor` assembly. The assembly becomes available when current local mirrors enable authoring. Runtime KitchenLib, Harmony, PlateUp and BepInEx APIs are outside this surface. Public serialized Unity asset roots elsewhere in Studio are serialization infrastructure rather than extension contracts; editor windows, repositories, asset readers and builders are implementation details.

The persisted Studio asset roots are `Graph.GdoBundleGraphAsset`, `Overlays.GdoOverlayAuthoringAsset`, and `Overlays.GdoLinkAuthoringAsset`, relative to `KitchenLib.Studio.Editor`. They are internal serialization infrastructure: Unity 2020.3 can discover and serialize them without public visibility. No public implementation asset roots are currently required. Their original script GUIDs, serialized field names, and schema identities are preserved; namespace migration metadata identifies their former `KitchenLib.Studio.Editor` names. Use Studio's menus and inspectors to author them, and retain all asset and script `.meta` files when transferring projects.

During `0.x`, supported C# API contracts may change incompatibly when documented in `CHANGELOG.md`. Strict semantic-version compatibility begins at `1.0.0`; subsequent breaking C# API changes require a major version. Serialized graph identities are protected independently from the first alpha: use extension-owned namespaced node type IDs (for example, `my-mod:recipe`), stable field/port keys and stable semantic type IDs. IDs and keys are non-empty, case-sensitive strings compared ordinally; CLR names are not persistent identities. Unknown node types, fields and endpoint records must be retained when integration persists graphs.

Implement `Graph.IStudioGraphNodeProvider` and explicitly call `KitchenLibStudioApi.RegisterGraphNodes(provider)` once per editor domain. Providers may return definitions in any order; registration stores them in ordinal `TypeId` order and rejects duplicate IDs atomically, including duplicates already registered. Empty providers are valid. A null provider, null definition sequence or null definition entry is rejected. Provider enumeration exceptions propagate to the caller without registering part of that provider.

`StudioGraphNodeDefinition` copies field and port descriptors, requires a projector and accepts an optional validator. Collection inputs are copied into read-only snapshots; field and port keys must be unique within their respective collections. `Authoring.StudioAuthoringValue` supports explicit null, Boolean, signed 64-bit integer, finite double, text and opaque stable authored-object reference values. A field default must match its declared kind or be explicit null. Required fields may start null while awaiting author input. References contain stable identifiers and provide no asset-loading access.

Validators receive `StudioGraphNodeData` plus a bounded `Validation.StudioValidationContext` and return structured findings with a stable code, severity, message and optional node/field/port location. Projectors receive the same read-only context and return `Build.StudioBuildProjection`, containing keyed scalar values and findings. An Error finding makes a projection unsuccessful; successful projection data must still pass Studio's built-in validation, audit and final bundle verification. These contracts expose no graph UI or filesystem/build service. Studio owns rendering, persistence, undo, connections and build orchestration.

Register on the Unity editor thread, including after each domain reload. Registration accepts `namespace:name` IDs: each part starts with an ASCII letter or digit and contains letters, digits, dots, underscores or hyphens; the name may also contain slashes. Field/port keys must be non-blank and contain no control characters. Successful registrations coalesce into one deferred refresh of open graphs; no asset refresh or domain reload is requested. The canvas **Create Custom** menu lists definitions in ordinal type-ID order. Studio renders all controls and ports and handles undo, movement, removal and save/reopen.

`StudioBuildProjection.Values` is keyed by declared output-port keys. Results may contain at most 256 values; each text/reference payload is limited to 65536 characters. Findings are limited to 256 per validator/projector result, with at most 65536 characters in each code/message. Unknown output keys, missing connected outputs, null results and thrown extension exceptions become blocking Studio diagnostics. Projectors should be deterministic and side-effect free: Studio can evaluate them repeatedly during validation, connection edits and builds. Custom diagnostic codes receive a Studio prefix so they cannot masquerade as built-in recoverable findings.

Use the public `KitchenLibStudioApi.GdoReferenceSemanticTypeId` constant for GDO-reference ports. Such an input accepts a built-in GDO output or a matching custom output; such an output can connect to a built-in GDO relationship input. Its projected value must be `StudioAuthoringValue.FromReference` containing an existing local or external graph GDO's stable node ID. The read-only context includes these GDO nodes, their connections and a `name` value. A projector can select a GDO from an input connection's endpoint without asset-reading access. Studio checks resolution and destination type, then uses the existing relationship companion, manifest, bundle, audit and final verification pipeline. An invalid reference blocks application atomically. Other semantic types match ordinally between custom ports; scalar outputs participate in declarative graph validation and do not create runtime files or manifests. Contexts contain authored data, not the results of other projectors; projection does not recursively execute upstream extensions.

Custom nodes persist only Studio-owned records: stable instance/type IDs, position and keyed fields encoded with a stable scalar discriminant and raw string payload. Connections reuse the graph's existing keyed endpoint records. The graph schema remains version 4 with an additive custom-node list; no existing field or manifest schema is renamed. Loading does not apply new defaults or rewrite existing fields. Unknown keys and unknown value encodings retain their raw payloads, including ordinally distinct keys. Missing definitions render a Studio diagnostic placeholder with retained ports and connections and block validation, projection and build. Re-registering a definition restores its controls without recreating the node. Unknown value encodings remain retained and block processing until supported; validators/projectors receive only decodable snapshots. No extension CLR type, delegate, validator, projector or UI object is serialized.

## Pre-build processors

Implement `Build.IStudioBuildProcessor` and call `KitchenLibStudioApi.RegisterBuildProcessor(processor)` on the Unity editor thread once per domain. `Id` uses the same namespaced syntax as graph type IDs, with a maximum of 256 characters. Studio captures `Id` and `Order` once, rejects ordinal duplicate IDs, and executes ascending `Order` then ordinal `Id`. At most 128 processors may register. Null, malformed, duplicate, oversized and reentrant registrations throw without publishing that registration; exceptions from identity/order getters propagate to the caller. Registration during the entire graph/packaging build is rejected, including from graph validators/projectors. Registrations clear before domain reload and require explicit registration in the next domain; registering does not request asset refresh or script reload.

The boundary follows graph preflight, custom-node validation/projection, graph application and final graph validation, plus validation of the original companion manifest. `Process(StudioBuildContext)` receives an immutable product snapshot before bundle staging or output writes. `ProductId` is the authored graph GUID (`selected-assets` for an internal direct build). Each `Nodes` entry identifies a selected local GDO by its asset GUID, uses `GdoReferenceSemanticTypeId`, and has empty `Connections`. `Values` exposes only existing supported companion fields, keyed exactly as `declaring-type|field-name`. These are opaque data keys, not CLR lookup or asset-reading capabilities.

Replace a field with `StudioBuildFieldChange(nodeId, fieldKey, value)` in `StudioBuildProcessorResult`. Supported values are text, enum integers, Boolean/integer/finite-number scalars, and references to other selected local GDO GUIDs. The initial scalar text is decoded as Boolean, then signed integer, then finite number in invariant culture. Accepted replacements retain their typed value in later snapshots: a Number containing `2.0` remains a Number even if its serialized scalar text is `2`. A replacement must keep the context value's kind. Reference replacements must also satisfy the field's actual expected GDO type. Nulls, external references, nested structures, collections and localization maps are not exposed for replacement. Processors cannot add fields, assets or connections, change identities, write native asset fields, or specify paths/files. Use graph authoring for those authoring operations.

The context permits at most 1024 local GDOs, 256 replaceable fields per GDO and 4096 replaceable fields overall. A result permits at most 256 changes and 256 findings. Each context/result string is limited to 65536 characters, and each complete context/result has a 1048576-character aggregate budget for its identifiers, keys, values and diagnostic text. Oversized contexts block processing; results exceeding these limits, duplicate node/field replacements, unknown fields, kind mismatches and unresolved references become deterministic build errors. Result constructors stop enumerating after the 257th item and reject null entries. Collections are copied into read-only snapshots.

Studio applies each result atomically to temporary companion copies and runs descriptor validation. Later processors see accepted replacements from earlier ones. A failing processor contributes a deterministic error, keeps the last accepted snapshot, and does not prevent later processors from reporting findings. An Error finding blocks the build. Extension finding codes are prefixed with `BuildFinding:<processor-id>:`; they cannot masquerade as recoverable built-in diagnostics. Throwing processors produce a fixed diagnostic without exposing arbitrary exception text.

Changes affect the built companion manifest only. Authored graph/GDO/companion state, unsaved values and dirty flags are restored after successful and failed builds; temporary copies are destroyed. Saving is scoped to that product's graph, local GDOs and companions; unrelated dirty assets keep their saved bytes, unsaved values and dirty flags. If processing fails, bundle staging and output files are untouched. Existing graph checks cannot be repaired or bypassed by a processor. Transformed companions still pass manifest/schema validation, normal bundle construction, package audit and `BundleOutputVerifier`. These callbacks must be deterministic and side-effect free; Studio supplies no filesystem or Unity object capability and cannot undo side effects an extension independently performs using unrelated editor APIs.

The exact supported public types are:

| Namespace beneath `KitchenLib.Studio.Editor.Api` | Types |
| --- | --- |
| Root | `KitchenLibStudioApi` |
| `Authoring` | `StudioAuthoringValueKind`, `StudioAuthoringValue` |
| `Graph` | `IStudioGraphNodeProvider`, `StudioGraphNodeDefinition`, `StudioGraphFieldDefinition`, `StudioGraphPortDefinition`, `StudioGraphPortDirection`, `StudioGraphPortCardinality`, `StudioGraphNodeData`, `StudioGraphConnection`, `StudioGraphEndpoint` |
| `Validation` | `IStudioGraphNodeValidator`, `StudioValidationContext`, `StudioValidationFinding`, `StudioValidationSeverity` |
| `Build` | `IStudioGraphNodeProjector`, `StudioBuildProjection`, `IStudioBuildProcessor`, `StudioBuildContext`, `StudioBuildFieldChange`, `StudioBuildProcessorResult` |

The package gate enumerates every C# source outside the explicit generation-template directory, rejects sources outside the authorized `Editor` tree, and pins public/protected signatures against this allowlist using ordinal, case-sensitive qualified names. Conditional sources are parsed separately under every combination of their conditional symbols, preserving actual type nesting; files exceeding eight symbols or having invalid syntax in a configuration fail the audit. Windows, controls, repositories, readers, paths, diagnostics and concrete builders remain internal. The three serialized roots described above remain internal serialization infrastructure. API contracts are editor-only and do not establish a runtime KitchenLib/Harmony/PlateUp/BepInEx compatibility API. The `0.x`/`1.0.0` and independently protected serialized-data policies above apply to every listed contract.

## Renaming and compatibility

Use **Rename Project** in the toolbar or **Rename GDO** on a local node. Review the old/new canonical identities, runtime IDs, and affected count, then explicitly acknowledge the compatibility warning to confirm. A project rename recalculates every local GDO identity; a GDO rename recalculates that GDO's identity. Changed IDs can break existing saves and external references in other mods. Even case-only renames require confirmation. Canceling changes nothing. Asset GUIDs and internal graph connections survive coordinated renames; avoid renaming owned assets directly in the Project window.

A successful rename clears the Unity editor's entire Undo/Redo history, as stated in the confirmation. Unity 2020.3 cannot reliably undo these filesystem operations or clear all creation records per affected object. Clearing history prevents older graph, GDO and companion snapshots from restoring identities that no longer match paths. Failed renames explicitly restore paths, identities, graph metadata and companion contents. Relationship projections are refreshed in the same transaction.

## Dough Ball in nine steps

1. Create the bundle project `MyBakery`.
2. Create a `KitchenData.ItemGroup` named `DoughBall`; its canonical identity is `mybakery:doughball`.
3. On its node choose **Add Relationship → Sets**.
4. In the Item Set node set `Min = 2`, `Max = 2`, and `IsMandatory = true`.
5. Add two entries to `Items` to expose **Items 0** and **Items 1** ports.
6. Add two external `KitchenData.Item` reference nodes, entering the known runtime IDs for Flour and Water from your target game version.
7. Connect Flour to **Items 0** and Water to **Items 1**.
8. Assign the Dough Ball prefab and any other intrinsic Item/ItemGroup fields on the expanded GDO node.
9. Save, resolve validation issues, and choose **Build**. The bundle contains the ItemGroup and a data-only overlay holding both external IDs; the runtime linker resolves those references in the game.

Use the actual Flour and Water runtime IDs from your target game version. Studio needs no PlateUp assemblies copied into the Unity authoring project.
